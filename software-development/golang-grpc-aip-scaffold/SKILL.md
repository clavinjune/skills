# Go gRPC/AIP/sqlc/wire Service Scaffold

Canonical worked example: `github.com/clavinjune/golang-scaffold`'s `bookinfo` domain (Books
nested under Authors) — a real, fully built and tested project, not a hypothetical. Read
`references/bookinfo-example.md` for full real code if the `templates/*.tmpl` files aren't
enough context. `templates/*.tmpl` are literal Go `text/template` files: fill in `Domain`
(PascalCase singular, e.g. `Book`), `domain` (lowercase singular, e.g. `book`), `Plural`/`plural`
(e.g. `Books`/`books`), `module`/`Module` (proto package + Go import alias, e.g. `bookinfo`), and
`modulePath` (Go module path, e.g. `github.com/clavinjune/golang-scaffold`). CLI-specific
templates live under `templates/cli/` — see the CLI scaffolding section below for which template
maps to which file.

## When to use
- Bootstrapping a brand-new Go backend that will use gRPC/HTTP + protobuf with Google AIP
  resource conventions, sqlc for DB access, and wire for compile-time DI.
- Adding a new **domain** (resource, e.g. "Invoice", "Customer") to an existing project already
  following this pattern — see **Adding a new domain: checklist** below.

## Directory shape (whole project)

```
<module>/
├── blueprint/                          # HAND-AUTHORED codegen sources (never generated)
│   ├── proto/<module>/v1/*.proto       # one proto file per resource/domain
│   └── sqlc/{schema.sql, query.sql}    # hand-maintained SQL — no migration tool
├── buf.gen.yaml / buf.yaml / buf.lock
├── sqlc.yaml
├── pkg/                                 # GENERATED output + thin interface contracts
│   ├── <module>/v1/*.pb.go             # generated by buf (message types; *_grpc.pb.go too if
│   │                                    # transport is real gRPC, not plain HTTP)
│   ├── sqlc/{db.go, models.go, querier.go, query.sql.go}  # generated by sqlc
│   ├── <domain>.go                      # HAND-WRITTEN: name helpers + Service/Repository interfaces
│   └── timestamp.go                     # HAND-WRITTEN: shared ParseTimestamp (AIP-142), once
├── internal/
│   ├── wire.go            # //go:build wireinject — top-level Wire() injector signature
│   ├── wire_gen.go         # generated by `wire`
│   ├── provider.go         # aggregates every domain ProviderSet + top-level Dependency struct
│   ├── httpjson/           # Read[T]/Write/WriteError generic helpers (encoding/json/v2)
│   ├── pagination/         # shared keyset/cursor token Encode/Decode
│   ├── serverutil/         # shared server bootstrap (NewLogger/Main/Serve) — see Pitfalls
│   ├── observability/      # optional: OTel interceptor/middleware, one root span per request
│   └── <domain>/           # one package per resource
│       ├── provider.go      # wire.NewSet + wire.Bind(interface, *impl) x3
│       ├── handler.go       # implements pkg.<Domain>Handler (routes on *http.ServeMux)
│       ├── service.go       # validation, error mapping, proto<->sqlc mapping, newID()
│       ├── repository.go    # wraps sqlc.Queries; sql.ErrNoRows -> pkg.ErrNotFound
│       └── *_test.go        # testify/suite or table-driven; real sqlite + httptest, no mocks
└── cmd/
    ├── <binary>-server/main.go   # composition root: opens DB, calls internal.Wire(db), registers handlers
    └── <binary>-cli/             # optional Cobra CLI client (see CLI scaffolding section)
```

## Steps

1. **Confirm parameters with the user before generating anything**: Go module path, first
   domain/resource name (e.g. `invoice`), whether SQLite (modernc.org/sqlite, no CGo) or another
   DB, transport (plain HTTP+JSON vs real gRPC), whether observability is wanted from day one.
   Don't assume — these are architecturally significant and belong in an ADR-0001, not silently
   copied from a prior project.

2. **Write the ADR first.** Create `docs/adr/0001-core-technology-stack.md` documenting: Go
   version, DB + driver, sqlc (no migrations, hand-maintained schema.sql), proto+buf (+ gRPC or
   plain HTTP, whichever was chosen), AIP resource conventions, google/wire (single top-level
   injector, not one per domain — see Pitfalls), testing approach (no mocks, real DB +
   bufconn/httptest).

3. **Scaffold config files** — copy from `templates/`:
   - `templates/sqlc.yaml` → project root, adjust `schema`/`queries`/`out` paths.
   - `templates/buf.gen.yaml` + `buf.yaml` → project root.
   - Add a `.gitignore` covering the codegen output dirs (`pkg/<module>/v1/*.pb.go`,
     `pkg/sqlc/`, `internal/wire_gen.go`) — `blueprint/` is the only source of truth, everything
     regenerable shouldn't be committed.

4. Follow **Adding a new domain: checklist** below for the first (and every subsequent) domain.

## Adding a new domain: checklist

Every new domain/resource — first one or the Nth — needs exactly these artifacts. Fill in
`templates/*.tmpl` (see header note on placeholder names) rather than writing from scratch;
cross-check against `references/bookinfo-example.md` if a template placeholder is unclear.

1. **Proto** — `blueprint/proto/<module>/v1/<domain>.proto` from `templates/domain.proto.tmpl`:
   `google.api.resource` annotation (`type`/`pattern`/`singular`/`plural`), `field_behavior` on
   every field (`IDENTIFIER`/`REQUIRED`/`OUTPUT_ONLY`/`OPTIONAL`), AIP-142 `create_time`/
   `update_time` (grill first — see Pitfalls), standard verbs `Create/Get/List/Update<X>`
   (AIP-131/132/133/134). For a **nested** resource, `parent` goes on `Create<X>Request` /
   `List<X>Request` instead of being embedded in `name`.
2. **SQL** — add a table to `blueprint/sqlc/schema.sql` (`id TEXT PRIMARY KEY`, `created_at`/
   `updated_at TEXT` with `strftime` defaults if timestamps are in scope) and
   `Create/Get/List/Update<X>` queries to `blueprint/sqlc/query.sql` (List uses
   `WHERE id > ? ORDER BY id LIMIT ?`, never OFFSET). If nested, add the parent's FK column and,
   if cross-parent listing is needed, a second `ListAll<X>` query with no parent filter
   (AIP-159 wildcard — see Pitfalls).
3. Run codegen: `buf generate && sqlc generate` (or the project's `make` targets for both).
4. **`pkg/<domain>.go`** from `templates/pkg_domain.go.tmpl`: `Format<Domain>Name`/
   `Parse<Domain>Name`, `<Domain>Handler`/`<Domain>Service`/`<Domain>Repository` interfaces,
   `Mutable<Domain>Paths`. A nested domain's name helpers should call the parent domain's
   exported helpers rather than re-deriving the parent's prefix.
5. **`internal/<domain>/{handler,service,repository,provider}.go`** from the matching
   `templates/*.tmpl` files (handler routes on `*http.ServeMux`; service does validation +
   `toProto()` mapping + `newID()`; repository wraps `sqlc.Queries`, maps `sql.ErrNoRows` to
   `pkg.ErrNotFound`; provider is the wire bindings).
6. **Register in `internal/provider.go`**: add the domain's `ProviderSet` to the aggregate
   `wire.NewSet(...)` and its Handler/Service/Repository fields to `Dependency` +
   `ProvideDependency`.
7. **Regenerate wire**: `go tool wire ./internal` (or `make wire`) → `internal/wire_gen.go`.
8. **Register the handler** in `cmd/<binary>-server/main.go`: `dep.<Domain>Handler.Register(mux)`
   (or the gRPC equivalent `Register<Domain>ServiceServer` if using real gRPC transport).
9. **Tests**: `internal/<domain>/{handler,service,repository}_test.go` in package
   `<domain>_test` (external test package), table-driven, real `:memory:` SQLite +
   `httptest.NewServer` (or `bufconn` for gRPC) — no mocks.
10. **If the project has a CLI**: add the full per-domain CLI package
    `cmd/<binary>-cli/cmd/<domain>/{provider,commands,table}.go` + its `<domain>_test.go` (see CLI
    scaffolding below) — a domain's CLI surface is a whole package, not a single file, mirroring
    the server side's `internal/<domain>/` shape.
11. **Update `blueprint/`-adjacent docs** if the project keeps an ADR/README describing the
    resource list — don't let it silently drift out of sync with what `buf generate` actually
    emits.

## CLI scaffolding (Cobra, `<binary> <verb> <resource>`, HTTP client abstraction, wired DI)

When the project also ships a CLI client, use **Cobra** in a `kubectl`-style `<verb> <resource>`
tree — not `<resource> <verb>`. This matches how `kubectl`/`gh`/`docker` read as natural language
("get pockets", "create pocket") and groups commands by action across resources rather than by
resource. The CLI mirrors the server's architecture end to end: one package per domain, wire DI,
and a real HTTP client abstraction living in `pkg/` — not a flat `cmd` package with hand-rolled
per-command HTTP calls.

### CLI directory shape
```
pkg/
├── <domain>.go                  # add <Domain>Client interface here, alongside Service/Repository
│                                  # (templates/cli/client_domain.go.tmpl)
└── client/
    └── <module>.go               # ONE struct implementing every domain's <Domain>Client over HTTP
                                    # (templates/cli/pkg_client.go.tmpl)
internal/
└── cliutil/
    └── cliutil.go                 # OutputFormat + Tabler/Namer + PrintResult, shared by every
                                     # domain's cmd package (templates/cli/cliutil.go.tmpl)
cmd/<binary>-cli/
├── main.go                       # calls cmd.NewRootCmd(nil).Execute()
└── cmd/
    ├── root.go                    # NewRootCmd: verb parents (get/create/update), lazily-addressed
    │                                shared client, wires + registers every domain (templates/cli/root.go.tmpl)
    ├── provider.go                 # top-level Dependency{<Domain>, ...} + ProviderSet aggregate
    │                                (templates/cli/provider.go.tmpl)
    ├── wire.go / wire_gen.go        # //go:build wireinject injector, same passthrough shape as
    │                                internal/wire.go (templates/cli/wire.go.tmpl)
    └── <domain>/                    # one CLI package per domain — mirrors internal/<domain>/
        ├── provider.go               # ProviderSet + Commands{Get,Create,Update} (templates/cli/domain_provider.go.tmpl)
        ├── commands.go                # newGetCmd/newCreateCmd/newUpdateCmd, all take the
        │                              pkg.<Domain>Client INTERFACE as a parameter — this is what
        │                              makes RunE testable (templates/cli/domain_commands.go.tmpl)
        ├── table.go                   # table/listTable wrapper types implementing cliutil.Tabler/Namer
        └── <domain>_test.go            # package <domain>_test, fakeClient + ProvideCommands(...) —
                                        no server, no HTTP (templates/cli/domain_commands_test.go.tmpl)
```

Command tree shape: `<binary>-cli get pocket <name>`, `<binary>-cli create pocket
--display-name=...`, `<binary>-cli update pocket <name> --display-name=...`. Each verb is a
parent command with one subcommand added per domain — adding a domain means one `Register(...)`
call in `root.go` and one `ProviderSet` entry in `provider.go`, not a new verb. There is no
separate `list` verb — see the get/list merge pitfall below.

### `pkg.<Domain>Client` — proto-shaped, not a `Service`-lookalike

`pkg/<domain>.go` gets a **`<Domain>Client` interface** using the exact same
`Create<Domain>Request`/`Get<Domain>Request`/etc. proto types the handler already decodes — not a
hand-rolled parameter list, and not a reuse of `<Domain>Service`. This mirrors what gRPC-generated
code already does: `<Domain>ServiceServer` and `<Domain>ServiceClient` are two separate
interfaces with the same RPC method names, one implemented by business logic + DB, one by a
network call. Keeping them distinct (even though they look almost identical) avoids the
confusing "service pretending to be a client" antipattern and matches that precedent exactly —
don't fight it for a cosmetic simplification.

`pkg/client/<module>.go` is the one HTTP-backed implementation of every domain's `<Domain>Client`
— genuinely public contract (any external Go program wants this, not just the CLI), so it lives
in `pkg/`, matching the existing convention that `pkg/` holds cross-consumer contracts.

### Wiring CLI subcommands with `wire`, same shape as the server

Once CLI commands depend on interfaces instead of a concrete client, the exact same wire pattern
used for the server applies: each domain's `cmd/<binary>-cli/cmd/<domain>/provider.go` exposes a
`ProviderSet` + `Commands` struct; the top-level `cmd/<binary>-cli/cmd/provider.go` aggregates
every domain's `ProviderSet` plus a `provide<Domain>Client(c *client.Client) pkg.<Domain>Client`
identity-bind function per domain (`wire.Bind` alone can't resolve wire's pass-through injector
argument to an interface — a tiny identity function stands in). `wire.go` declares the
`//go:build wireinject` injector signature; `go tool wire ./cmd/<binary>-cli/cmd` regenerates
`wire_gen.go`. Adding domain N+1 means: one new package, one field on `Dependency`, one
`ProviderSet`/bind-function pair — nothing else changes.

**Ordering wrinkle vs. the server's wire.go**: Cobra needs every subcommand already added to the
tree before it parses args (routing walks already-added children), but `--addr` isn't known
until flags are parsed. So `root.go` builds the shared `*client.Client` eagerly with an empty
`BaseURL`, wires the whole `Dependency` and registers every domain's commands immediately, then
fills in `BaseURL` from the parsed flag inside `PersistentPreRunE` — before any subcommand's
`RunE` fires. Don't defer the wire-and-register step into `PersistentPreRunE` itself; the
subcommands need to exist in the tree first for cobra to route to them at all.

### Pitfalls
- Resist making it `<resource> <verb>` (e.g. `pocket create`) even though the proto/domain
  package structure is resource-first — the CLI's UX contract is verb-first per kubectl
  convention; don't let the backend's resource-oriented package layout bleed into the CLI's
  command grouping.
- Don't build a `Service`-shaped interface for the CLI-to-server contract (e.g. hand-rolled
  `CreateAuthor(ctx, displayName string) (...)`) — take the same proto Request/Response types the
  server handler decodes, so the CLI, any other Go caller, and the server all speak the identical
  contract with zero re-derivation.
- `internal/cliutil`'s `Tabler`/`Namer` methods must be **exported** (`TableHeaders`, not
  `tableHeaders`) once the flat single-package CLI splits into per-domain packages — an
  unexported interface method can't be implemented from a different package, a mistake that only
  surfaces once you've already deleted the old flat files.

## Pitfalls

### Architecture
- Don't generate a wire injector per domain — one top-level `Wire()` in `internal/` is simpler
  and avoids N nearly-identical injector functions.
- `blueprint/` is the source of truth; anything in `pkg/<module>/v1` or `pkg/sqlc` is
  regenerated and should never be hand-edited.
- Layering is strict: handler never touches sqlc, repository never returns proto types. The
  service's `toProto()` mapper (sqlc model <-> proto message) is business-logic mapping between
  two concrete internal types, so it stays in the domain package, not `pkg`. Resource-name
  helpers (`Format<Domain>Name`/`Parse<Domain>Name`) and the mutable-fields allowlist
  (`Mutable<Domain>Paths`) ARE public contract, though — they belong in `pkg/<domain>.go`,
  exported, not buried in `internal/<domain>/`, because any external caller (CLI, frontend BFF, a
  nesting child domain) needs the exact same logic and shouldn't hand-duplicate it.
- `ListX` repository methods return a **value** slice (`[]sqlc.X`, matching what sqlc's generated
  query already returns) — not `[]*sqlc.X`, which forces a pointless boxing loop just to satisfy
  a self-imposed pointer signature. Single-item `Create`/`Get`/`Update` still return `*sqlc.X`
  since sqlc hands you one value there.
- A single shared constant beats one per domain (`pkg.DefaultPageSize`, not
  `internal/<domain>.defaultPageSize` duplicated N times) — anything that's the same value by
  convention across domains belongs in `pkg` once.
- Ask before assuming DB choice / observability approach — these are ADR-level decisions per
  project, never copied silently from a prior project.

### Pagination
- Implement real keyset pagination (not `next_page_token` always empty) as soon as the CLI/
  frontend needs stable multi-page listing: a shared `internal/pagination` package
  (`Encode(lastID) string` / `Decode(token) (string, error)`, base64-opaque token) plus
  `WHERE id > ? ORDER BY id LIMIT ?` (never OFFSET, which can skip/repeat rows under concurrent
  writes). Service fetches `limit+1` rows to detect "more pages exist" without a COUNT query,
  trims to `limit`, encodes the last row's id as `next_page_token`. `lastID` threads through
  `Repository.ListX(ctx, pageSize int32, lastID string)` — stays out of `pkg`, it's an internal
  DB cursor, not part of the AIP contract (the token itself is opaque to callers).
- **CLI list UX: no page-size/page-token flags, ever.** `get <domain>` (list mode) transparently
  loops calling the server following `next_page_token` until empty, aggregating all pages before
  printing — matching `kubectl get`'s behavior exactly. Only a server-to-server caller should
  ever see/pass page_token/page_size.
- **AIP-159 wildcard collection id for cross-parent listing**: when a nested resource's List
  needs a "list across every parent" mode (e.g. all Books regardless of Author), don't do
  client-side fan-out (list all parents, then List per parent — a hidden N+1 with no matching
  API capability). Use AIP-159's real mechanism: the parent path accepts a literal `-` as the
  wildcard collection id (`authors/-`), and the List query drops the parent-scope filter when it
  sees that literal. Go's `net/http` mux pattern (`GET /authors/{author}/books`) already matches
  `/authors/-/books` for free — no new route needed, just branch in the repository on `authorID
  == pkg.WildcardCollectionID` ("-", exported next to the other name helpers) to skip the
  `WHERE author_id = ?` clause (add a second sqlc query, e.g. `ListAllBooks`). CLI: the child
  domain's scoping flag (`--author`) becomes optional — omit it to default to the wildcard parent,
  matching kubectl's implicit-scope vs `-A`/`--all-namespaces` split, except here "list
  everything" is the CLI default and the flag is the narrowing option.

### CLI UX
- **`get`/`list` verb merge**: don't ship separate `get` (get-one) and `list` (list-all) verb
  parents — merge into a single `get <domain> [name]`, matching kubectl's own `get pods` (list) /
  `get pod <name>` (get-one). Dispatch on arg count (`cobra.MaximumNArgs(1)`): 0 args → list-all
  helper (auto-paginates internally), 1 arg → get-by-name. Stick with the bare singular resource
  name for the `Use` field — no singular/plural alias dance, that's purely cosmetic.
- **Output formats — kubectl-style `-o table|wide|json|yaml|name`**: don't hand-roll a single
  JSON-only `print()`. Build `printResult(w, format, v, table, names)` in the CLI package:
  `json`/`yaml` always marshal the raw proto response value (yaml.v3 doesn't know proto's `json`
  tags, so round-trip `json.Marshal` → `any` → `yaml.Marshal` rather than hand-maintaining
  parallel yaml-tagged types); `table`/`wide` render via a `tabler` interface
  (`tableHeaders(wide bool) []string`, `tableRows(wide bool) [][]string`) on a thin per-domain
  wrapper (`type authorTable struct{ *bookinfov1.Author }`) using `text/tabwriter`; `name` renders
  via a parallel `namer` interface (`resourceNames() []string`) on the same wrapper, printing
  bare resource names one per line — no `kind/` prefix needed since an AIP resource name
  (`authors/{id}`) already fully encodes what it is. **Bug to avoid**: never pass the table
  wrapper to the json/yaml path — its unexported embedded field marshals to `{}`; always pass the
  raw proto value separately (`c.print(w, &resp, authorTable{&resp}, authorTable{&resp})` — same
  wrapper satisfies both `tabler` and `namer`). Bind `-o`/`--output` as a persistent root flag
  (default `"table"`), read through a closure (`func() outputFormat`) on the shared client struct
  — cobra only populates the bound variable after `Execute()` parses flags, so a closure captured
  at registration time reads the right value once `RunE` fires, not a plain field copied too
  early.
- **Config source split by binary role**: long-running servers (`cmd/*-server`) take ALL runtime
  config from env vars (no `flag` package — servers are launched by process
  managers/containers, where env vars are the native injection mechanism). Interactive clients
  (`cmd/*-cli`) use cobra flags instead (a human is typing directly, so `--help`/discoverability
  matter). Don't mix the two within one binary.
- **RunE must be testable — take the interface as a parameter, not a closed-over concrete
  client.** `newGetCmd(c pkg.<Domain>Client, format func() cliutil.OutputFormat) *cobra.Command`
  — because the constructor takes the small domain interface rather than building/closing over a
  concrete `*client.Client` internally, a test can hand it a hand-written `fakeClient` (real
  struct with per-method closures, no mocking framework — same "no mocks" rule as the server
  side) and call `cmds.Get.Execute()` directly. No server, no `httptest.NewServer`, no wire tree
  needed for RunE-level tests — reserve `httptest`/full-binary tests for the handful of true
  end-to-end smoke cases. See `templates/cli/domain_commands_test.go.tmpl`.
- **CLI test files use the external `_test` package, same as the server side.** `package
  <domain>_test`, driving through the exported `<domain>.ProvideCommands(...)` entry point and
  `Commands.Get/Create/Update` fields — never reach into unexported `newGetCmd` from a test; if a
  test needs it, that's the signal the constructor should be exported or the test should go
  through `ProvideCommands` instead.

### AIP-142 timestamps & ids
- **create_time/update_time — grill before adding, don't cargo-cult.** The real test: does
  something concrete downstream read this field and change behavior based on it (same test as
  the CRD-vs-AIP fit check)? `create_time` earns its keep with a "recently added" view/sort or
  audit requirement; `update_time` earns its keep once optimistic concurrency or client-side
  freshness checks are needed; `deleted_at`/soft-delete needs a real `Delete` verb plus an
  explicit undo/audit requirement first — don't add it pre-emptively (every existing query would
  need `WHERE deleted_at IS NULL` retrofitted, plus id-reuse semantics decided). If the project
  explicitly frames itself as a reusable scaffold for others to copy, lean toward including
  `create_time`/`update_time` anyway — the marginal cost is low and every downstream project
  wants at least `update_time` eventually. Name them `create_time`/`update_time` (proto
  `google.protobuf.Timestamp`, `OUTPUT_ONLY`) per AIP-142, not `created_at`/`updated_at` — don't
  break AIP naming pattern just for timestamps. Store as SQLite TEXT via
  `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')` (schema default for create, explicit SET on every
  `Update<X>` query); convert via one shared `pkg.ParseTimestamp` helper (cross-domain contract
  logic, written once).
- **UUIDv7 for resource ids, not UUIDv4.** `google/uuid`'s `uuid.NewV7()` embeds a millisecond
  timestamp in its leading bits, so plain string/byte ordering is chronological — this directly
  reinforces keyset pagination (`WHERE id > ? ORDER BY id`), giving creation-order-for-free where
  UUIDv4 gives random order, and better index locality on real (non-SQLite) databases. Put a
  small `newID() string` helper per domain's `service.go` (falls back to `uuid.NewString()` only
  if `uuid.NewV7()` errors) rather than calling it inline at each `Create<X>` call site.

### Operational plumbing
- Long-running server `main()`: derive ctx from `signal.NotifyContext(context.Background(),
  os.Interrupt, syscall.SIGTERM)`, not a bare `context.Background()` inside `run` — otherwise
  there's nothing to select on for graceful shutdown. `http.Server` + goroutine `ListenAndServe`
  feeding a buffered error channel, `select` between that channel and `ctx.Done()`, then
  `srv.Shutdown(context.WithTimeout(...))` on signal. `slog` writes JSON to `os.Stdout` (stdout is
  the convention for structured logs meant for a pipeline, not stderr), Info by default,
  `AddSource: true` only at Debug (source lookups aren't free, don't pay them at Info in prod).
- **Once a second server-role binary exists, factor the above into `internal/serverutil`** rather
  than copy-pasting `main()`/`run()` boilerplate: `NewLogger(debugEnvVar string) *slog.Logger`,
  `Main(logger, run func(ctx) error)` (wraps `run` with `signal.NotifyContext` + error logging +
  `os.Exit(1)`), `Serve(ctx, logger, addr, handler) error` (the ListenAndServe/select/Shutdown
  dance). Each binary's `main()` becomes `serverutil.Main(logger, func(ctx) error { return
  run(ctx, logger) })`; `run` ends with `return serverutil.Serve(ctx, logger, addr, someHandler)`.
  This is `internal/`, not `pkg/` — plumbing for this project's own binaries, not a contract
  other services import.

### Style
- Package-level declarations: `const (...)` then `var (...)` then `type (...)`, grouped, near the
  top of the file after imports (standard gofmt-safe Go). Does NOT extend to function-local
  declarations — Go idiom is declare-where-used (`:=` at first use), not front-loading a
  function-start `var` block (that's a C/Pascal habit that fights Go's scoping).
